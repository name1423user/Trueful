# ADR-012: Workspace状態永続化と破損復旧機構

- Status: Accepted
- Date: 2026-08-06
- Supersedes: なし(ADR-011「Workspace Lifecycle Management」の未決定事項を解消するもの)

## Context

ADR-011でWorkspaceの新規作成フロー・再アクティブ化フローを設計したが、以下の3点は未決定として残されていた。

1. アプリ起動時クリーンアップの実行条件(毎回実行 or 異常終了時のみ)
2. Dormant → Archiveへの自動遷移条件
3. SQLite `workspace`テーブルへの状態列・時刻列の正式なマイグレーション定義

また、実装着手にあたり「破損したWorkspaceをどう検知し、どう扱うか」の設計が新たに必要になった。

## Decision

### 1. 起動時クリーンアップ

毎回無条件で実行する。

異常終了時のみに限定する案も検討したが、「異常終了かどうか」の判定ロジック自体が新たな不具合の要因になりうる(判定を誤ると、本来クリーンアップすべきタイミングで動作しない)。実装初期段階では、判定条件を持たないシンプルな方式を優先する。

実装時の制約:毎回実行しても起動体験を損なわないよう、クリーンアップ処理自体の軽量性を維持すること。

### 2. Dormant → Archive遷移

DB上の状態(`status`列)ではDormantと区別しない。Archiveは表示層でのみ区別される概念とし、「dormantになってからの経過日数」を都度計算して判定する。状態を書き換える処理自体を持たない。

理由:状態遷移処理を持つと、書き換え漏れやタイミングのズレによる不整合のリスクが生じる。都度計算方式であれば、この種の不整合は原理的に発生しない。既存のLRU・再アクティブ化フローのロジックもDormant/Archiveの区別なく共通利用できる。

境界日数はハードコーディングせず、定数として一元管理する。

### 3. `workspace`テーブルのスキーマ

| 列名 | 型 | デフォルト値 | 役割 |
|---|---|---|---|
| `status` | TEXT(`active` \| `dormant`) | `active` | Workspaceの現在の状態 |
| `last_used_time_ms` | INTEGER | 作成時刻 | 最後に開いた時刻。LRU判定に使用 |
| `dormanted_time_ms` | INTEGER, NULL許容 | `NULL` | 非アクティブになった時刻。Archive判定(経過日数計算)に使用 |

「最後に開いた時刻」と「非アクティブになった時刻」は意味が異なる(LRU判定 vs Archive判定)ため、1列に統合せず分離した。`dormanted_time_ms`のデフォルトを`NULL`としたのは、未発生のイベントを`0`等の数値で表現すると事実と異なる記録になるため。列名はSQLの慣習に従いスネークケースを採用し、Renderer層(キャメルケース)との命名上の境界を明確にする。

### 4. 破損検知・復旧機構

Workspaceの破損を以下の3パターンに分類する。

| パターン | 内容 | 復旧方針 |
|---|---|---|
| ① マニフェストJSON自体が破損(パース不可) | 書き込み中のクラッシュ等 | SQLite側のバックアップから復元を試行 |
| ② マニフェストは読めるが必須項目が欠落 | 作成フロー途中の中断(未完成) | 復元ではなく作成フローの続きへ誘導 |
| ③ マニフェストは正常だが参照先ファイルが実体として存在しない | ユーザーによる手動削除・移動 | 復旧不可。報告のみ |

Workspace ID自体が破損している場合は上記に含めず、識別不能・復旧不可として扱う(バックアップとの紐付けが成立しないため)。

破損確認処理は、単純な真偽値ではなく該当パターン(①/②/③)を返す設計とし、呼び出し側(起動時クリーンアップ、再アクティブ化フロー)がパターンに応じた対処を選択できるようにする。

### 5. バックアップ機構

マニフェストの写しとSHA256チェックサムを、`workspace`テーブルとは別テーブルに保持する。

- 別テーブルとする理由:マニフェストJSONは相対的にサイズが大きく、一覧表示等で頻繁にアクセスする`workspace`テーブル本体に含めると通常動作のパフォーマンスに影響しうる
- チェックサムを保持する理由:バックアップ自体の破損可能性を考慮し、バックアップの正当性そのものを検証可能にするため
- 更新タイミング:マニフェスト変更のたびに毎回更新し、バックアップが常に最新の正しい状態を反映するようにする
- 実装配置:バックアップ処理は独立した単機能の部品として実装し、マニフェスト保存処理の内部から呼び出す。これにより単体再利用性を保ちつつ、保存とバックアップの呼び忘れを構造的に防止する

### 6. ユーザー通知

パターンごとに通知の強度を分ける。深刻度のみでなく「ユーザーが取りうる行動の性質」を基準とする。

| パターン | 通知強度 | 理由 |
|---|---|---|
| ①(自動復元済み) | 軽量(トースト等) | ユーザーの対応が不要なため |
| ②(未完成) | 中(誘導型ポップ) | 作業の続行という前向きな行動に誘導できるため |
| ③(復旧不可) | 重(確認ダイアログ) | アプリ側で解決不能であり、ユーザーの判断が必須のため |

## Consequences

- Dormant/Archiveの区別をDB状態として持たないため、既存のLRU等のロジック改修が不要になる一方、表示のたびに経過日数計算が発生する。Workspace数が多い場合の計算コストは実装時に留意する
- バックアップテーブルの世代管理方針(最新1件のみ保持 / 複数世代保持)は本ADRの時点では未決定であり、別途スキーマ設計時に確定させる
- チェックサム検証を復元処理の前後どちらのタイミングで行うかも未決定であり、実装時に確定させる

## 未決着事項(次回検討)

- バックアップテーブルの世代管理方針
- チェックサム検証のタイミング(復元前/復元後)
- 破損確認処理と起動時クリーンアップ・再アクティブ化フローとの具体的な組み込み順序
