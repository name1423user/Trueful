# ADR-014: workspaceFile.ts のアトミック書き込みとエラーラップ設計

- **Status**: 採用
- **Date**: 2026-09-06
- **関連**: ADR-011, ADR-012

## Context

`workspaceFile.ts` の `writeJsonFile` は、当初 `fs.writeFileSync(path, data)` で本番ファイルへ直接上書きする実装だった。この実装には2つの懸念がある。

1. 書き込みの途中でプロセスがクラッシュした場合、本番ファイルが破損した状態のまま残る可能性がある。
2. 書き込み失敗時に例外を投げっぱなしにしても、呼び出し元は「一時的な失敗か、根本原因が解消されるまで再試行しても無駄な失敗か」を区別する材料を持てない。

ADR-012で確定した破損検知・階層的通知の設計を実現するには、`writeJsonFile` の失敗が呼び出し元にとって十分に解釈可能な情報を持つ必要がある。

## Decision

`writeJsonFile` を「一時ファイルへの書き込み→`renameSync`による本番ファイルへの切り替え」という2段階の書き込みに変更する。また、書き込み失敗時は元の `NodeJS.ErrnoException` をラップした独自エラークラス `WorkspaceFileError`（`path` と元エラーを保持）を re-throw する。

## Rationale

- `fs.writeFileSync` は「既存の中身を読んで修正する」処理ではなく「渡された内容で丸ごと上書きする」処理のため、一時ファイル名を固定（`path + '.tmp'`）にしても、前回クラッシュ時の残骸を事前にチェック・削除する必要はない。次回の書き込みで自動的に上書きされる。
- `renameSync` はOSレベルでほぼ一瞬の切り替えとして扱われるため、書きかけの状態が外部から観測されない。ただし一時ファイルと本番ファイルは同一ファイルシステム上に置く必要がある（異なるファイルシステムをまたぐrenameは実体のコピーが必要になり、アトミック性の前提が崩れる）。今回は同一ディレクトリ内に配置するため、この制約は設計上問題にならない。
- `renameSync` 失敗時、本番ファイル（`path`）は一切変更されないため、既存データは破損しない。ただし一時ファイルは残ったままになり、かつ失敗原因（権限不足・ディスク容量不足など）が解消されない限り再試行しても直らない可能性がある。この「失敗の種類」を呼び出し元が判別できるようにするため、Node.jsのファイルシステム系エラーが持つ `.code`（`ENOSPC`、`EACCES`等）を、独自クラスで構造化して保持する方針とした。
- `.code` を `message` 文字列に埋め込む案は却下した。文字列パースに依存した判定は文言変更で壊れるため、専用プロパティとして持たせる方が壊れにくい。
- 元の `error` オブジェクトを直接改造してプロパティを追加する案（wrapせずmutateする）も却下した。TypeScriptの型（`NodeJS.ErrnoException`）に存在しないプロパティを後から追加するのは型システムを迂回する行為であり、また `instanceof` によるエラー種別の判定ができなくなる。

この判断はLayer 2（Failure Friendly）に直結する。失敗を防ぐのではなく、失敗したときに原因を追跡できる形で情報を残す、という設計方針の具体化である。

## Alternatives Considered

| 選択肢 | 評価 | 却下理由 |
| --- | --- | --- |
| tmp→rename + カスタムエラークラスでラップしてre-throw | ○ | （採用） |
| 直接上書き（`fs.writeFileSync(path, data)`のみ） | ✕ | クラッシュ時に本番ファイルが破損する可能性がある |
| 戻り値に `{ path, status }` を持たせる方式 | ✕ | 呼び出し元が `status` のチェックを怠っても型チェックでは検出できず、エラーが見落とされるリスクがある |
| 既存の `error` オブジェクトを直接mutateしてプロパティ追加 | ✕ | 型定義にないプロパティの追加は型安全性を損なう。`instanceof` による種別判定もできない |
| tmpファイル名をUUID化して衝突を回避 | △ | 「後勝ち（last-write-wins）」問題自体は解決しない。呼び出し元が単一プロセスからの逐次呼び出しである現状では、固定名で問題ない |

## Consequences

**得られるもの**

- クラッシュ時にも本番ファイルが破損しない
- 呼び出し元が `.code` を見て「再試行可能な失敗か」を判別できる材料を持てる
- デバッグ時に元のエラー情報（スタックトレース含む）を失わない

**引き受けるもの**

- `renameSync` 失敗時、一時ファイルがディスク上に残り続ける可能性がある（次回の正常な書き込みで自動的に上書きされるため実害は限定的）
- 「後勝ち（last-write-wins）」問題は未解決のまま残っている。複数の呼び出し元から同一ファイルへの書き込みが競合するケースは今回のスコープ外

**影響範囲**

- `services/workspaceFile.ts` の `writeJsonFile` 実装
- 今後実装する `workspaceDB.ts` など、同様の書き込み処理を持つ `services/` 配下のファイルにも、同じ設計パターン（アトミック書き込み・エラーラップ）を適用する候補になる

## 再検討条件

- 複数プロセス・複数箇所からの同時書き込みが要件として発生した場合（「後勝ち」問題への対応が必要になったとき）
- `renameSync` 失敗時の一時ファイル残留が、実運用上ディスク容量などの問題を引き起こした場合
