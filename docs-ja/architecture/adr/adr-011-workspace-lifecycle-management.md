# ADR-011: Workspaceライフサイクル管理(LRU・確認/報告方針・処理分割)

**ステータス**: 決定済み
**日付**: 2026-08-05
**関連**: [ADR-002](../../docs-ja/architecture/adr/adr-002-sqlite.md)（SQLite採用）, [data-schema.md](../../docs-ja/architecture/data-schema.md), [MVPスコープ](../../docs-ja/roadmap/mvp-scope.md)

## コンテキスト

Workspaceの「新規作成」フローおよび「休止(Dormant)中Workspaceの再アクティブ化」フローを設計する過程で、以下の論点が持ち上がった。

- フルアクティブWorkspaceは最大5個。超過時は最も長く非アクティブなものからLRU方式でDormant化する仕様がMVPスコープに存在する
- LRU実行時にユーザー確認を挟むべきか、自動実行すべきか
- 再アクティブ化しようとしているWorkspace自身が、LRUの検索対象に巻き込まれないか
- 破損確認・LRU本体・ステータス管理・通知処理をどう分割すべきか
- 孤児データ(作成途中で中断されたWorkspace)のクリーンアップをどこに実装するか
- SecurityProfileの警告表示のタイミング

## 決定

### 1. LRU(Dormant化)は確認なしで自動実行し、事後報告のみ行う

Dormant化は「破棄ではなく休止、いつでも復帰可能」という可逆な操作であるため、事前の確認ダイアログ(割り込みコストの高い手段)は不要と判断する。実行後にトースト等の軽量な通知で結果を伝える。

**理由**: 取り返しのつかない操作(完全削除など)にのみ確認を要求し、可逆な操作には確認を求めない、という基準を統一する。確認ダイアログの濫用はConsent Fatigue(同意疲れ)を招く。

### 2. LRU本体は「除外Workspace ID」を引数として受け取る

再アクティブ化しようとしているWorkspace自身がLRUの選定対象(検索条件)に含まれないよう、除外対象のWorkspace IDをLRU本体の入力として明示的に渡す。実行順序による回避(「先に他を処理してから対象を追加する」等)には依拠しない。

**理由**: 実行順序に依存した回避策は、検索条件そのものを見直さない限り再発するバグの温床になる。条件式に明示することで再発を防ぐ。

### 3. LRUは「対象選定とDormant化の実行」のみを担当する単機能コンポーネントとする

破損確認・ステータス確認/更新・事後報告は、LRUから独立した別コンポーネントとして切り出す。LRUはこれらを呼び出す側(オーケストレーター、後述のflows層)から利用される1つのserviceとして扱う。

**理由**: 破損確認や事後報告は、LRU以外の文脈(手動Dormant化、削除処理など)からも将来利用される想定であり、LRU内部に密結合させると再利用性を損なう。

### 4. Main層のWorkspaceドメインを`services`(単機能部品)と`flows`(オーケストレーター)に分割する

```
main/
  workspace/
    services/   # 破損確認、LRU本体、ステータス確認・更新、SecurityProfile警告リクエスト
    flows/      # 作成フロー、アクティブ化フロー(servicesを束ねて実行)
  shared/       # 事後報告など、複数ドメインから利用される汎用コンポーネント
  bootstrap/    # 起動シーケンス(各ドメインの初期化処理を呼び出すのみ)
```

`components`という命名は避ける(Renderer層のUI部品を指す語として既に意味が固定されているため衝突する)。`utils`は「特定ドメインに依存しない汎用処理」を指す語として、Workspace専用ロジックの命名には採用しない。

### 5. 孤児データ(作成途中で中断されたWorkspace)のクリーンアップは、判定・実行ロジックをWorkspaceドメイン側(`services`)に置き、起動シーケンス(`bootstrap`)側は「起動タイミングでの呼び出し」のみを担当する

**理由**: 孤児データの判定にはWorkspaceのデータ構造(SQLite `workspace`テーブルのステータス列等)への理解が必要であり、これをドメイン外に置くとドメイン境界を越えた密結合が生じる。「いつ実行するか(タイミング)」と「何を実行するか(処理内容)」は別の関心事として分離する。

### 6. SecurityProfileの警告表示は、LRU完了後・実際にWorkspaceを開く直前に表示する

**理由**: LRU実行前に警告を表示すると、LRUが何らかの理由で中断された場合に「警告を見たのに開けなかった」という無意味な割り込みが発生する。警告は「これから確実に開かれる」タイミングでのみ表示することで、この矛盾を避ける。

## 未決定・今後の検討事項

- アプリ起動時クリーンアップを毎回無条件で実行するか、異常終了時のみに限定するかは未確定
- Dormant → Archiveへの自動遷移条件(一定期間経過での自動化、または手動のみか)は未設計
- SQLite `workspace`テーブルへの列追加(ステータス列、最終アクセス時刻列)は方針として合意済みだが、正式なマイグレーション定義はまだ行っていない

## 影響範囲

- `main/workspace/` 以下のディレクトリ構成
- `data-schema.md` の `workspace` テーブル定義(列追加が必要)
- 今後実装する Command Palette / Inspector Bar 等、他ドメインの設計にも同じ `services` / `flows` パターンを踏襲する想定
